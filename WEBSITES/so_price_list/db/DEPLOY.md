# Eschler Price Book — deployment

Three pieces: database, API, web app. The API is the one with a trap — read
section 2 before copying anything over it.

---

## 1. Database

`gemmasoft`. **Everything the application owns lives in schema `SO`** — the
tables and the package — with the customer list of values in `LOV`:

| Object | Schema |
|---|---|
| `so_price_list_header`, `so_price_list_detail` | `SO` |
| `so_price_list` (the raw flat extract) | `SO` |
| `P_SO_PRICE_LIST_PKG_*` — 13 procedures | `SO` |
| `P_LOV_PKG_select_customer_list` | `LOV` |
| `so_price_list_bak_20260907` | `dbo` — a point-in-time backup, deliberately left behind |
| `customers`, `so` | `dbo` — not ours, never move them |

Run the scripts in this folder in this order:

    move_tables_to_SO_schema.sql             one-off; idempotent, safe to re-run
    P_SO_PRICE_LIST_PKG_01_select.sql        reads, incl. get_price
    P_SO_PRICE_LIST_PKG_02_update.sql        upserts + name validation
    P_SO_PRICE_LIST_PKG_03_delete_copy.sql   soft deletes + copy a list
    P_SO_PRICE_LIST_PKG_04_grid_shape.sql    header grid settings + row edit
    P_LOV_PKG_select_customer_list.sql       customer LOV
    add_active_flag.sql                      active column on the detail table
    add_active_flag_raw.sql                  active column on the raw flat table

Each script drops and recreates what it owns, so re-running is safe. The two
`add_active_flag*` scripts also create a staging table used by the backfill in
`..\to_excel\backfill_active_flag.ps1`; drop it once the backfill is done.

That leaves 14 procedures: 13 under `SO.P_SO_PRICE_LIST_PKG_*` plus
`LOV.P_LOV_PKG_select_customer_list`.

### ⚠ `dbo.so` is a prefix of `dbo.so_price_list`

If you ever rewrite schema references with find-and-replace, match the **longer**
string first. A naive `dbo.so` → `SO.so` also rewrites `dbo.so_price_list`, and
worse, silently redirects `dbo.so` — the **sales order table**, which is not ours
and must stay in `dbo`. `dbo.customers` is in the same category.

After any such rewrite, confirm nothing was missed:

```sql
SELECT o.name, d.referenced_schema_name, d.referenced_entity_name
FROM   sys.sql_expression_dependencies d
JOIN   sys.objects o ON o.object_id = d.referencing_id
WHERE  o.name LIKE 'P_SO_PRICE_LIST_PKG%'
  AND  d.referenced_entity_name LIKE 'so_price_list%'
  AND  ISNULL(d.referenced_schema_name,'dbo') = 'dbo';
```

Zero rows is the pass.

### The API needs no redeployment when tables move

The API names **procedures only** — never a table — so a schema move on the
tables is invisible to it. `CommandType.StoredProcedure` is set in exactly one
place ([api-dotnet/Db.cs](../api-dotnet/Db.cs)), and there is no SQL text
anywhere in the API. Redeploy the procedures, and the running binary picks up
the change on its next call.

Rules live in the procedures too — currency must be USD/THB, `qty_max >=
qty_min`, `active` must be Y/N, list names unique, dates ordered — raised with
`RAISERROR` so they hold no matter what calls them. The API maps those to HTTP
400 with the message intact.

## 2. API — `V:\ESHWeb\SoPriceListApi`

ASP.NET Core 8, published **self-contained win-x64**, so the server's installed
.NET runtimes do not matter and the existing net7.0 `V:\WebAPI` is untouched.
IIS hosts it through `AspNetCoreModuleV2` with `hostingModel="inprocess"`.

Build and publish:

    dotnet publish -c Release -r win-x64 --self-contained true -o publish

`web.config` is generated by the SDK on every publish — do not hand-write one,
it will only drift from the real `processPath`.

### ⚠ Redeploying: you MUST take the app offline first

`hostingModel="inprocess"` means the API runs inside the shared `w3wp` process,
which holds an open handle on `SoPriceListApi.dll`. A plain copy does **not**
fail loudly — it copies `SoPriceListApi.exe` and `web.config`, silently skips the
locked DLL, and leaves a new exe running yesterday's code. robocopy returns exit
**11** when this happens; anything `>= 8` means files failed.

`app_offline.htm` is the fix, and it is **per application, not per pool** — the
ASP.NET Core Module shuts down only this app and releases its locks. `SoStatus`,
`CmrStatus`, `StenterView` and the Login site keep serving throughout, even
though they share the pool. (IIS Manager cannot help here: it stops *sites* and
*pools*, never a single application.)

    1. echo "Updating" > V:\ESHWeb\SoPriceListApi\app_offline.htm
    2. wait ~8 seconds for the app to unload
    3. robocopy <publish> V:\ESHWeb\SoPriceListApi /E        (no /PURGE — see below)
    4. del V:\ESHWeb\SoPriceListApi\app_offline.htm
    5. icacls V:\ESHWeb\SoPriceListApi /grant "NT AUTHORITY\IUSR:(OI)(CI)(RX)" /T /C

Then **verify the DLL actually landed** — the whole point of the exercise:

    compare LastWriteTime of SoPriceListApi.dll locally vs on the server

Two things that will bite:

- The file must sit in the **application root**, not a subfolder.
- If `app_offline.htm` is left behind the API stays down until it is deleted.
  Check for a stale one at the start of every deploy.

Never use `/PURGE` on this folder: it holds 361 runtime files, and a purge
against a partial source sweeps the runtime out from under the app.

### First-time IIS setup

Under the site that serves `ESHWeb` (port 3001), right-click → *Add Application*:

    Alias            SoPriceListApi
    Physical path    V:\ESHWeb\SoPriceListApi
    Application pool any (the runtime is bundled; No Managed Code is fine)

Check:

    http://<host>/SoPriceListApi/health   ->   {"ok":true,"db":"connected"}

The SQL connection string is in `appsettings.json` in that folder, in plain
text — the app pool identity should be the only account with read access.

## 3. Web app — `V:\ESHWeb\SoPriceList`

A Vite build shaped like its CRA siblings (`static/`, `index.html`,
`web.config`), so it deploys the same way `SoStatus` and `CmrStatus` do.

    npm run build
    robocopy <dist> V:\ESHWeb\SoPriceList /E /PURGE
    icacls V:\ESHWeb\SoPriceList /grant "NT AUTHORITY\IUSR:(OI)(CI)(RX)" /T /C

`/PURGE` is wanted here — it clears the previous fingerprinted
`static/js/*.js` and `*.css`, which otherwise pile up. It is safe because
`web.config` and `config.js` are both in `web/public/`, so every build emits
them and the purge cannot strip them. (They used to live only on the server,
and a purge deleted them.)

### The IUSR permission, or you get a silent 401

Static files are served to the anonymous account **`IUSR`**, not the app pool
identity. A folder created fresh over the mapped drive does not inherit that
right, and every request under `/SoPriceList/` then returns **401** — with no
`WWW-Authenticate` header, because IIS is refusing on the ACL rather than asking
for credentials. The API is unaffected, since in-process ASP.NET Core runs as the
pool identity, which makes the failure look stranger than it is.

`SoStatus` has the ACE that makes it work:

    NT AUTHORITY\IUSR    ReadAndExecute, Synchronize    (explicit)

So re-run the `icacls` line after **every** deploy — a new `static` folder needs
it too.

### Pointing at the API

`config.js` sets the API base and is deliberately **not** fingerprinted, and
`web.config` marks it no-cache, so the API can be moved by editing one line on
the server with no rebuild:

    window.__PRICE_LIST_API__ = '/SoPriceListApi';

A relative path means same-origin — no CORS, no hard-coded host or port. Use a
full URL only if the API moves off this site.

## Launching from VB.NET

    http://<host>/SoPriceList/?user_id=SURES

| Parameter   | Effect                                                        |
|-------------|---------------------------------------------------------------|
| `user_id`   | Shown read-only; becomes `created_by` / `updated_by` on edits  |
| `header_id` | Opens straight to that price list                              |
| `list_name` | Same, by name instead of id                                    |
| `article`   | Pre-fills the article filter                                   |

Example for order entry:

    http://<host>/SoPriceList/?user_id=SURES&list_name=CENTER&article=255484

There is no login in front of the page, so `user_id` is whatever the caller
says it is. That is fine on an internal network and worth revisiting if the
site is ever reachable from outside.

## Smoke test after any deploy

    http://<host>/SoPriceListApi/health                     {"ok":true,...}
    http://<host>/SoPriceList/robots.txt                    2 lines of text, NOT html
    http://<host>/SoPriceList/config.js                     one line of JS, NOT html

If `robots.txt` or `config.js` come back as HTML, the app is falling through to
the Login site's SPA rewrite: either the IIS application is missing, or `IUSR`
cannot read the folder.

Sibling apps should keep answering 200 throughout an API deploy — that is the
check that `app_offline.htm` scoped the restart correctly:

    http://<host>/SoStatus/     http://<host>/CmrStatus/     http://<host>/StenterView/
